# SQL Memory Agent

This is a new research project for studying how a SQL Agent can manage and use cross-task long-term memory through reinforcement learning.

This repository is independent from EDError. It must not copy, import, or depend on EDError code, environments, outputs, datasets, or Git history.

## Research Question

The project studies a SQL Agent that solves a stream of database tasks while maintaining a long-term memory store across tasks. The central question is not only whether memory retrieval improves future task performance, but also whether the agent can learn when to keep, update, delete, or temporarily ignore old memory after database contents or schemas change.

Two core questions are fixed at project initialization:

1. Does saved memory from previous tasks help the agent solve later unseen tasks?
2. After a database update, should old memory be updated, deleted, or temporarily withheld from use?

## Current Status

A minimal no-download, no-model, no-GPU toy experiment now exists. It is only a protocol validation harness; its deterministic SQL solver is a testing stub and must not be reported as a real model result.

The toy harness verifies that:

- the memory store starts empty;
- each task retrieves memory once before solving;
- memory written by the current task is not available until later tasks;
- a schema change from database v1 to v2 quarantines stale v1 memories before retrieval;
- paired evaluation compares empty memory against selected memory on the same database snapshot;
- final correctness dominates turn-count efficiency in scoring.

Run the compact deterministic demo log:

```bash
cd /root/autodl-tmp/sql-memory-agent
/root/miniconda3/bin/python scripts/run_toy_experiment.py
```

What the toy data does:

- `retail_v1.sqlite` has `orders`, `stores`, `cities`, and `refunds.refund_amount`.
- `retail_v2.sqlite` changes the refund schema to `refund_events.returned_amount`.
- Gross sales pick `Metropolis`, while net sales after refunds pick `Gotham`, so the data distinguishes ?did not deduct refunds? from ?deducted refunds?.
- A v1 memory that depends on `refunds.refund_amount` is quarantined before the v2 task, so it cannot be retrieved after the schema update.

## Reproducibility Plan

A future reproducible run should record:

- Git commit SHA of this project.
- Dataset version and exact split construction.
- Database snapshot ID for every task.
- Fixed SQL Agent model/tool configuration.
- Memory policy or RL checkpoint being evaluated.
- Random seeds for paired comparisons.
- Per-question memory retrieval result and final answer.
- Evaluation script version and environment metadata.

No experimental result should be reported from this repository unless it is generated by committed code and a recorded config.

- A learned RL policy for ADD/UPDATE/DELETE/KEEP/QUARANTINE.
- A reliable semantic branch verifier beyond this deterministic toy execution check.
