# Experiment Protocol

This document records the initial experimental contract for the SQL Memory Agent project. It is a protocol, not a result report.

## 1. Core Questions

The project must answer two core questions:

1. Does saved memory help future new tasks?
2. After a database update, should old memory be `UPDATE`d, `DELETE`d, or temporarily withheld from use?

The second question is part of the main problem, not an optional follow-up. Memory can become stale when the database changes, and a memory policy must be evaluated on whether it handles that staleness safely.

## 2. Task Stream and Memory Causality

The main experiment starts from an empty memory store.

Tasks arrive in a predetermined order. Memory produced by task `t` may only be used by later tasks `t+1...n`; it must not be used by the same task that created it, and it must never use future task information.

This means each run must log:

- task order,
- memory store state before each task,
- retrieved memory for the current task,
- new or changed memory after the current task,
- database snapshot used by the task.

## 3. Single Retrieval Per Question

Each question retrieves memory once.

The retrieved set is fixed before the SQL Agent begins solving the question. The agent may reason over the retrieved memory, but it must not issue repeated memory searches during the same question unless a later protocol revision explicitly adds and tests a multi-retrieval setting.

## 4. Fixed SQL Agent Across Comparisons

The SQL Agent itself must stay fixed in both control experiments and memory-strategy training.

When comparing memory strategies, the following must remain identical for paired examples:

- database snapshot,
- model and decoding settings,
- tools,
- maximum turns / budget,
- random seed pair,
- prompt template except for the memory block,
- evaluator.

The experiment compares memory policies, not changing SQL Agents.

## 5. Empty Memory Is Allowed

A memory strategy may return an empty memory set. Empty retrieval is a valid action and should not be treated as system failure.

Comparisons must include combinations where no memory is provided, because the first task in a stream necessarily has no prior memory and later tasks may be safer without stale memory.

## 6. Paired Evaluation Rule

The same question must be evaluated under matched conditions:

- same database snapshot,
- same fixed SQL Agent,
- same tool budget,
- paired random seed,
- same answer evaluator,
- only memory input differs.

This paired setup is required to attribute changes in outcome to the memory policy.

## 7. Primary and Secondary Metrics

Final correctness is the primary metric.

Only among correct outcomes should the experiment compare efficiency metrics such as:

- SQL Agent turns,
- tool calls,
- number of retrieved memories,
- number of memory writes/updates/deletes,
- latency or token cost, if measured consistently.

A faster wrong answer is not better than a slower correct answer.

## 8. Branch Verification

A branch, memory update, or semantic claim may be used for training only after reliable verification.

A branch may be considered verified only if its correctness can be established by a trusted mechanism such as exact SQL execution equivalence, deterministic database checks, manually validated gold evidence, or another documented verifier.

Branches that cannot be judged must not be recorded as successful training examples. They may be logged as unknown, but unknown must not be converted into positive reward.

## 9. Train / Validation / Test Isolation

Training, validation, and test streams must be isolated.

For test questions, the following must never enter the agent input or historical memory:

- correct SQL,
- final answer,
- future task information,
- labels derived from future tasks,
- memory generated by later test items,
- any validation/test oracle not available at deployment time.

Evaluation may use gold answers after the agent finishes, but that information cannot be fed back into the tested agent.

## 10. Database Update Handling

When a database update occurs, a memory policy may choose among at least these actions:

- keep memory unchanged,
- update memory,
- delete memory,
- mark memory stale,
- temporarily withhold memory from retrieval,
- request verification before reuse.

The protocol should separately log whether a memory is factually wrong, schema-stale, value-stale, or merely irrelevant.

## 11. Reporting Requirements

Every experiment report must state:

- whether memory started empty,
- task order construction,
- database snapshot construction,
- SQL Agent identity and frozen settings,
- memory retrieval limit and retrieval algorithm,
- memory write/update/delete policy,
- branch verification method,
- train/validation/test isolation method,
- exact metrics and evaluator.

No table should imply that an unresolved design choice has already been experimentally validated.
